# Gate G3: optimised CUDA kernels, release 0.3.0

Oct 26, 2026 · Phase 3 of the [execution roadmap](../execution-roadmap.md)

**Decision: approved.** In the `fixed` numeric mode the CUDA backend runs kernels written for CUDA, 71× /
30× (small), 31× / 14× (medium) and 17.6× / 12.2× (large) faster than PyFWI 0.1.10 for the forward
modelling / gradient, above the targets of the analysis, within the tolerances of OpenCL on the whole
matrix of the golden masters. `auto` is the default backend. OpenCL keeps the `legacy` mode as its default
(decision below). Six open points, none of which blocks Phase 4, are listed at the end; the first two
depend on the project owner. An overview with figures: [overview.md](../overview.md).

## Decision: OpenCL stays `legacy` by default

The roadmap leaves to this gate whether OpenCL also switches to `fixed` by default. It does not, in 0.3.0:
the `fixed` results have not been reviewed by a geophysicist yet (open point 3 of G2), and the users of
the OpenCL engine, the default of a plain installation, keep exactly the results of 0.1.10. `fixed` stays
the default of the CUDA backend, which a user gets only by installing a `cuda` extra, and either backend
runs either mode on request (`PYFWI_NUMERICS`). To be revisited after the review.

## What Phase 3 changed and found

- **Native kernels, then one optimisation per step.** Written for CUDA, the kernels first gave the bits of
  the OpenCL files (3.2); then multiplications by `1/dx` (3.3), one thread per receiver for sources and
  receivers (3.4), fusion (3.5: 5 → 3 launches per forward step, 8 → 5 per gradient step), the time step
  on the device (3.6), CUDA graphs (3.7), checkpoints on the GPU (3.8), the damping read only at the
  borders (3.10), the shots in batches with the checkpoints of a batch copied in one launch (3.9), and the
  idle gaps of the timeline removed (3.11).
- **Most of the small scenario was host time.** Graphs (1.75×), checkpoints on the device (2×) and batches
  (2×) gave most of its 10× over 0.2.0; one copy per component and shot cost about 6 µs of host time each,
  which only a profile showed.
- **The row past the field edge.** The stencils still read one row past the field (open point 4 of G2);
  with batches that row is a row of margin after every slot, not the first row of the next shot, which
  would change the results when a source sits on row 0 (found and tested in step 3.9).
- **Measuring on a desktop GPU.** The same GPU draws the desktop and changed its state during the day
  (the same engines took up to 16 % longer in the evening): comparisons were made within one session,
  with the previous commit in a worktree when needed.

## Open points

1. **Self-hosted GPU runner** not registered (owner action, unchanged since G0). Every commit of Phase 3
   ran the fast suites on NVIDIA, on POCL and in the reference environment, and the slow suites on NVIDIA
   and on POCL, before being pushed.
2. **Nsight Compute** still cannot read the GPU counters (owner action, roadmap pending action 1): the
   bandwidth per kernel is an estimate.
3. **Review of the `fixed` results by a geophysicist** (G2 open point 3, unchanged); it decides the default
   numeric mode of OpenCL.
4. **Another GPU generation** (roadmap pending action 4): the block rule and the batch size were measured on
   the RTX 3060 only; `PYFWI_CUDA_BLOCK` and `PYFWI_CUDA_BATCH` let them be tuned elsewhere.
5. **Recomputation tier of the checkpoints** (step 3.8): when the checkpoints fit in neither the GPU nor the
   host memory, nothing recomputes them yet; the boundary saving of Phase 4 (step 4.2) addresses the memory.
6. **Halo cells instead of the row past the field edge** (G2 open point 4): the stencils keep reading one
   row past the field, made safe by the margins and by the row between slots.
