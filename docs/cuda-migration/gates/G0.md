## What Phase 0 found

Beyond the problems listed in the analysis, Phase 0 measured or found, in PyFWI 0.1.10:

- out-of-bounds reads and writes in the kernels (stencils and five unbounded receiver loops), which
  make some results depend on the memory layout and can crash the NVIDIA kernel
  (`CL_OUT_OF_RESOURCES`) after a few propagations in one process;
- race conditions when a source sits on a receiver cell or two receivers share one (the default
  `acq_type=2` geometry);
- a wrong gradient with the default `chpr=0`;
- an approximate gradient in general (31 % median error against finite differences);
- an impulsive source injection that excites grid-scale noise at grid spacings of 4 to 6 m;
- absolute optimiser tolerances that stop L-BFGS at iteration 0 on realistic data;
- the effects of NumPy 2 (imports, and a last-bit change of the PML profile) and SciPy ≥ 1.8
  (`MemoizeJac`, removed arguments of `fmin_l_bfgs_b`);
- PyOpenCL 2026 running 44-60 % slower than PyOpenCL 2022 on the small scenario.

The [roadmap](../execution-roadmap.md#current-state) records each finding with the step that handles it.

## Exceptions (owner actions)

1. **Nsight Compute** cannot read the GPU counters (`RmProfilingAdminOnly: 1`). Needed from Phase 2
   on, to measure the bandwidth of each CUDA kernel. How to enable: roadmap, pending action 1.
2. **Self-hosted GPU runner** not registered. Until it is, the GPU, slow and reference suites run on
   the RTX before each commit instead of in CI. How to register: [self-hosted-runner.md](../self-hosted-runner.md).
