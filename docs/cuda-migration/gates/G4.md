# Gate G4: opt-in features, release 0.4.0

Oct 27, 2026 · Phase 4 of the [execution roadmap](../execution-roadmap.md)

**Decision: approved, with the geophysical review open.** Release 0.4.0 adds five opt-in features, all off by
default: the cost function on the GPU, boundary saving, FP16 fields, the shots in several processes and CUDA
tensors in `torchfwi`. Four meet their tolerance in a complete inversion; the FP16 mode does not, and is
documented as a mode for modelling and gradients only. The defaults did not change: the same results (the
parity report is that of 0.3.0), the same speed (77× / 32×, 29.5× / 14.4× and 17.0× / 11.9× faster than 0.1.10
for the forward modelling / gradient of the small, medium and large scenarios). The complete inversions of
both backends are ready for the review of a geophysicist, which the gate asks to record: it is an action of
the owner, and until it is done OpenCL keeps the `legacy` mode by default (the decision of G3).

## The FP16 mode does not invert

The target of the roadmap was a final model error at most 10 % above that of float32. Half precision keeps
11 significant bits: the rounding of every update leaves an error about 60 dB below the peak of the fields.
The late, attenuated part of a recording falls under it, and the error changes chaotically with the model, so
the misfit is rough (a change of 0.002 m/s moved it by 6 %) and the line search of L-BFGS finds no descent.
Scales that are powers of two, and rounding toward zero in the damped cells, were tried (step 4.3). The mode
stays for what it does well, modelling and gradients (seismograms 44 to 57 dB, gradients 33 to 46 dB of
float32, half the memory, up to 2× faster when the checkpoints then fit on the GPU), as the CHANGELOG and the
README say; the FWI test stays a strict `xfail`, so that a future fix is noticed.

## What Phase 4 changed and found

- **Opt-in, one variable each.** `PYFWI_CUDA_COST`, `PYFWI_BOUNDARY_SAVING`, `PYFWI_FP16`, `PYFWI_CUDA_DEVICES`,
  and tensors on a CUDA device: nothing changes for a user who sets none of them, and each one fails with a
  clear message where it cannot run (boundary saving and FP16 need the native kernels).
- **The host was the bottleneck of an inversion, not the GPU** (step 4.1): a third of an evaluation was the
  multi-scale filters on the host; on the GPU, in float32 (GeForce cards run FP64 at 1/64 of the rate).
- **Memory, not speed, is what boundary saving buys** on a 12 GB card: a little slower when the checkpoints
  fit, much faster when they do not.
- **Reproducibility across processes** (step 4.4): the gradients of the shots are added on the host in the
  order of the shots, so any number of processes gives the same bits.
- **Complete inversions on both backends** (step 4.6): CUDA and OpenCL in the same mode give the same
  estimates within 1.7 % of what the inversion recovers after 45 iterations (rounding amplified by the line
  searches), the geophysical metrics within 0.008; `legacy` against `fixed` up to 15 %.

## Open points

1. **Geophysical review** of the validation report (owner action); it decides the default numeric mode of
   OpenCL (G3).
2. **FP16 inversions** (above): a mode that keeps the late part of the recordings, for example float32 for
   the fields of the last part of the recording or compensated updates, would be new work.
3. **Scaling over several GPUs** is not measured: one GPU here (roadmap pending action 4). Two processes on
   the RTX give the bits of one process; one worker costs +2 %.
4. **Host tier for the boundary-saving store**: a store larger than the GPU (the 50 shots of the large
   scenario: 32 GB) is refused with a clear message.
5. **`torchfwi` without the host round trip**: CUDA tensors reach CuPy without a copy, but the propagators
   take NumPy arrays, so the model and the results cross the host.
6. **Unchanged since G3**: the self-hosted GPU runner and the Nsight Compute counters (owner actions), another
   GPU generation, halo cells instead of the row past the field edge. A gap of about 2 ms before the time loop
   of the forward modelling with boundary saving (small scenario) was seen in the timeline and not
   investigated.
